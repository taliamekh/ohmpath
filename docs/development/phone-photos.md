# Optional phone photo transfer

The phone transfer is a separate, explicitly started desktop helper for moving a still image into Photo help. It does not start Photo help's subscription reasoning turn, import a confirmed measurement, open a continuous camera feed, use audio, or control hardware. The laptop must still show the received image for review and wait for the user's **Ask** click.

`createPhonePhotoBridge({ onPhoto, networkInterfaces?, now?, testAdapter? })` exports four operations:

- `interfaces()` lists current, non-internal RFC 1918 IPv4 interfaces as `{name,address}`. The desktop should show these choices to the user rather than silently choosing one.
- `await start({address})` checks that exact address against a fresh interface inventory, binds only to it on an ephemeral port, and returns `{active,url,expires_at,address,received_count}`. Starting twice is rejected. The URL is `http://<chosen-address>:<port>/#token=<random-32-byte-token>`. Neither `0.0.0.0` nor loopback is a production choice.
- `status()` returns the same shape. The transfer expires after 15 minutes; an expired token is invalidated even if the timer has not fired yet.
- `await stop()` invalidates the token, aborts pending callback signals, destroys connections, and closes the listener. Restart generates a new token. Call this when the user closes transfer and during application shutdown.

The page is self-contained HTML, CSS, and JavaScript from `GET /`. It loads no remote resources, reads the token from the URL fragment into memory, and removes the fragment from browser history. The user taps the file input to take or choose a photo. The page locally decodes it, draws a maximum 2400-pixel-side copy, re-encodes JPEG under 2 MB, and shows that prepared preview. Only an explicit **Send to Ohm Path** click posts it. The optional question is text data capped at 4,000 characters. A successful transfer says to review and press Ask on the laptop; it never invokes Ask itself.

`POST /photo` requires the exact selected Host, matching same Origin, an exact bearer token, an RFC 1918 peer address, JSON content type, and a bounded body. The bridge enforces 3 MB JSON, 2 MB decoded PNG/JPEG, at most 4096 pixels per side and 8 megapixels, six upload attempts and sixty total requests per minute, one outstanding upload, short header/body/socket timeouts, and at most eight connections. All other routes and methods are rejected. The `onPhoto({bytes,mime_type,question,signal})` callback receives validated bytes; the desktop integration must use its existing native image decode/re-encode path and return a short opaque receipt string. It must honor `signal` if it performs asynchronous work, since stop and expiry cannot undo a callback's already committed side effect. The bridge never trusts phone-provided dimensions or file paths and sends only a generic receipt or error to the phone.

This is **HTTP on a trusted local network**, not a secure internet pairing service. Someone who can observe that network may see the image or bearer header; the URL fragment keeps the token out of ordinary HTTP request lines but does not encrypt it. Do not expose the port through a router, tunnel, public Wi-Fi, or firewall rule. Users should select a trusted private interface, stop transfer when finished, and use direct Photo help upload if a suitable network is unavailable. There are no cookies, external assets, account changes, media files, or token logs.

Node-only tests inject an RFC 1918 interface inventory and a `testAdapter` that maps the listener to `127.0.0.1`; it is constructor-only test plumbing, never request or renderer data. Those tests validate the boundary without opening a LAN listener or invoking Electron, a provider, camera, microphone, or hardware. Phone browser compatibility, Windows firewall behavior, and the laptop UI handoff still need integration and user-visible verification.
